# Подтверждение действий по почте (magic link)

Как устроено подтверждение по ссылке из письма и как с ним работает фронт.
Реализация: `api/src/modules/mail/`, клиент — `front/src/features/email-verification/`.

## Почему токен, а не uuid пользователя

В ссылку кладётся 256-битный случайный токен (`randomBytes(32)`, base64url),
в базе хранится только его SHA-256 — как у refresh-токенов. Uuid пользователя
не подошёл бы: он не секрет, ходит в API, в истории и в матчинге, и любой, кто
его видел, подтверждал бы чужое удаление аккаунта.

Токен живёт 30 минут, срабатывает один раз и привязан к одному действию:
ссылкой, выпущенной под смену почты, нельзя подтвердить удаление аккаунта.

## Две ступени

Переход по ссылке только ставит отметку «это я» (**confirm**). Само действие
выполняется там, где пользователь его начал, когда он нажмёт «Я перешёл по
ссылке» (**consume**).

Так сделано по трём причинам: письмо открывают в браузере, где сессии
приложения нет; превью-сканеры почтовых клиентов ходят по ссылкам сами и не
должны ничего выполнять; почтовый модуль не должен знать, как удалять аккаунты
и менять телефоны.

Исключение — `verify_email`: у него подтверждение адреса и есть всё действие
целиком, экрана «Я перешёл по ссылке» в регистрации нет, поэтому он
завершается прямо на confirm.

## Ручки

| Метод                                | Авторизация | Назначение                                    |
| ------------------------------------ | ----------- | --------------------------------------------- |
| `POST /email/verifications`          | Bearer      | Выпустить тикет и отправить письмо            |
| `POST /email/verifications/confirm`  | нет         | Отметить переход по ссылке (пропуск — токен)  |
| `GET /email/verifications/:id`       | Bearer      | Состояние тикета — за этим ходит «Я перешёл»  |

`POST /email/verifications` принимает `{ purpose, email? }` и отдаёт
`{ id, email, expiresAt }`. `email` из запроса учитывается только у
`change_email` — это и есть проверяемый адрес; у остальных действий письмо
уходит на почту аккаунта.

Статусы тикета: `pending` → `confirmed` → `consumed`; плюс `expired`.

Повторная отправка — не чаще раза в минуту на пару (аккаунт, действие); новое
письмо гасит прежний тикет, поэтому клиент обязан запомнить новый `id`.

## Действия и кто расходует тикет

| purpose          | Письмо уходит на         | Расходует                                       |
| ---------------- | ------------------------ | ----------------------------------------------- |
| `verify_email`   | адрес аккаунта           | сам confirm                                     |
| `change_email`   | НОВЫЙ адрес из запроса   | `PATCH /profile/email { verificationId }`        |
| `change_phone`   | подтверждённый адрес     | `POST /profile/phone { phone, code, verificationId }` |
| `delete_account` | подтверждённый адрес     | `DELETE /profile { verificationId }`             |

Адрес при смене почты берётся из тикета, а не из финального запроса: подменить
подтверждённый адрес на последнем шаге быть не должно.

`change_phone` и `delete_account` требуют **подтверждённой** почты — письмо на
непроверенный адрес не доказывает ничего. Если подтверждённой почты нет:
смена номера недоступна (настройки профиля объясняют это у карандаша), а
удаление аккаунта проходит без письма — иначе аккаунты, заведённые до появления
почты, нельзя было бы удалить вовсе.

## Где почта берётся

Первый раз — при регистрации: `POST /profile { name, role, email }` сохраняет
адрес **неподтверждённым** и сразу шлёт письмо, но регистрацию на него не
завешивает. Недоступный Postbox или занятый адрес не должны оставлять
пользователя без профиля на последнем шаге, а заставлять незрячего
пользователя посреди регистрации уходить в почтовый клиент и возвращаться —
плохой сценарий. Подтвердить адрес можно позже, из настроек профиля.

Уникальность адреса — частичная, только среди подтверждённых
(`UQ_email_accounts_verified_email`). Иначе опечатка в чужой почте навсегда
заняла бы адрес его настоящему владельцу.

## Смена номера телефона

Два независимых доказательства, оба обязательны:

1. переход по ссылке из письма на подтверждённую почту — аккаунт ваш (этого не
   сделает тот, кто просто перехватил сессию);
2. код из звонка на **новый** номер — номер рабочий и ваш. Без этого шага
   опечатка отрезала бы человека от аккаунта навсегда: вход только по телефону.

Меняется строка в `phone_accounts`, а не связь: uuid остаётся прежним, поэтому
история, сессии и уже выданные JWT продолжают работать, и заново входить не
нужно ни на одном устройстве.

## Локальная разработка

Без `POSTBOX_API_KEY`/`POSTBOX_API_SECRET` письмо не отправляется, а целиком
печатается в лог `api` вместе со ссылкой — ровно как `OTP_BYPASS` для кодов:

```
docker logs vizhu_api --tail 50 | grep magic-link
```

В production отсутствие ключей — ошибка 500, а не молчаливая заглушка.

`APP_URL` задаёт домен в ссылке (`$APP_URL/magic-link?token=...`) и должен
совпадать с доменом фронта; в dev-compose это `http://localhost`.
